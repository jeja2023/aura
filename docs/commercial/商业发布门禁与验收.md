# 商业发布门禁与验收

## 使用方式

先执行 `dotnet build Aura.sln -c Release` 生成候选构建，再复制并填写 `service-profile.template.json`，完成产品、技术、SRE 和交付审批后将 `status` 改为 `approved`，填写审批引用和批准人。自动化门禁使用该候选构建执行 `--no-build` 测试，避免覆盖正在验收的运行实例；测试开始后不得追溯降低阈值。

Windows：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\ops\aura-ops.ps1 release-gate --profile .\artifacts\service-profile.json --evidence-dir .\artifacts\field-evidence --output .\artifacts\release-gate --run-automated --real-dependencies --target-hardware --secret-scan-clean
```

Linux：

```bash
sh ./scripts/ops/release-gate.sh --profile ./artifacts/service-profile.json --evidence-dir ./artifacts/field-evidence --output ./artifacts/release-gate --run-automated --real-dependencies --target-hardware --secret-scan-clean
```

脚本生成机器可读 JSON、人工可读 Markdown 和逐项日志。结论为 `blocked` 时退出码为 2，适合 CI/CD 阻断。三个环境断言只能在对应审批证据存在时传入，不能用于绕过缺失检查。

## 证据目录

每项现场证据保存为 `<check_code>.json`，结构参见 `release-evidence.template.json`。`passed` 必须同时包含 `exitCode=0` 和非空 `artifactUri`。所有环境字段都会按秘密键名脱敏。

| check_code | 最低证据 |
| --- | --- |
| dotnet_tests | Release 构建与 .NET 测试日志 |
| python_tests | AI pytest 日志和数据集版本 |
| frontend_lint | ESLint 结果 |
| postgres_migrations | 迁移 001-036、pending=0、unknown/drift=0 |
| arango_real | 真实 ArangoDB 3.12 投影、断点追平、全量重建、N 跳和最短路径 |
| pgvector_target_scale | 10 万、100 万、目标规模 Recall@1/5/10、P95/P99、QPS、资源 |
| backlog_recovery | 5 倍突发、下游故障一小时、重复事件和恢复追平 |
| backup_restore | 全量/增量备份、校验、空环境恢复、RPO/RTO |
| upgrade_rollback | 0.2.0 到 0.3.0 升级和批准恢复点回滚 |
| browser_matrix | 目标 Chromium/Edge、1366 桌面和窄屏、角色与键盘回归 |
| linux_scripts | Linux 构建机镜像构建、推送、保存、离线包安装和校验 |
| security_privacy | SAST/依赖/秘密扫描、对象授权、删除与证据导出检查 |
| oidc_idp | 客户真实 IdP 的 PKCE、签名、映射、禁用、登出和恢复 |
| real_device_adapter | 真实型号/固件八项合同测试与报告 URI |

## API 归档

门禁报告可通过 `/api/commercial/service-profiles` 建立画像、审批后调用 `/api/commercial/release-gates` 创建运行，再将每项 JSON 提交到 `/{gateRunId}/evidence` 并完成门禁。后端重复执行同样的 14 项完整性和环境断言判定；例外必须填写影响、补偿措施、责任人、批准人及 30 天内关闭日期。
