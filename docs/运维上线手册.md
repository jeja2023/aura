# 运维上线手册

本文合并原部署手册、上线检查清单、readiness 说明与 AI 生产检查清单，作为当前版本上线与日常巡检的统一入口。

## 1. 部署入口

- Docker 编排：`docker/docker-compose.yml`
- Docker 环境模板：`.env.docker.example`
- 启动：`docker/up.ps1` 或 `docker/up.sh`
- 停止：`docker/down.ps1` 或 `docker/down.sh`
- 健康检查：`docker/check.ps1` 或 `docker/check.sh`

上线前复制模板：

```powershell
Copy-Item .env.docker.example .env.docker
```

然后替换 `.env.docker` 中的镜像标签、端口、数据库密码、JWT/HMAC 密钥与管理员密码。

## 2. 基础服务

统一 Compose 会拉起：

- PostgreSQL：业务主库
- Redis：缓存、限流、重试队列、SignalR backplane
- ArangoDB：由 PostgreSQL Outbox 投影生成的空间与关系图；图数据可重建，不保存业务权威事实或新业务向量
- AI：FastAPI 特征提取与检索服务
- API：.NET 中枢服务
- `arango-init`：确保 `ARANGO_DB` 数据库存在
- `db-migrate`：执行 PostgreSQL 增量迁移

首次部署服务器可以临时连接互联网，将 `IMAGE_PULL_POLICY` 设为 `missing` 并使用 `docker/up.ps1 -Build` 或 `docker/up.sh --build` 完成镜像拉取/构建/启动。部署成功后断开互联网，并改回 `IMAGE_PULL_POLICY=never`。

## 3. 上线前检查

- [ ] `.env.docker` 中所有 `REPLACE_*` 占位值已替换。
- [ ] `AllowedHosts` 已配置实际域名或局域网 IP。
- [ ] `JWT__KEY` 与 `SECURITY__HMACSECRET` 为足够长的随机值。
- [ ] `POSTGRES_PASSWORD`、`ARANGO_ROOT_PASSWORD`、`AURA_ADMIN_PASSWORD` 不使用默认值。
- [ ] 使用服务器 GPU worker 时，`gpu-bridge` 网络存在，GPU 共享卷内模型路径与 `docker-compose.yml` 内置默认值一致；如现场服务名、项目名或模型名不同，已覆盖同名环境变量。
- [ ] `IMAGE_PULL_POLICY` 与实际镜像来源一致。
- [ ] 如服务器已有其他 Redis 使用默认端口，`REDIS_PORT` 已保持为 `6380` 或改为其他未占用宿主机端口；容器内连接仍使用 `redis:6379`。
- [ ] API、AI、PostgreSQL、Redis、ArangoDB 端口未被占用。
- [ ] 临时联网部署期间使用安全组/防火墙限制访问来源，部署完成后按要求断开互联网。
- [ ] 如启用 `AURA_API_KEY`，API 与 AI 使用同一个值。
- [ ] 如启用 Prometheus 或 OpenTelemetry，仅允许内网监控系统访问相关端点。

### 3.1 Security hardening checklist
- [ ] Reverse proxy/TLS termination: keep `SECURITY__COOKIES__FORCESECURE=true` and `SECURITY__FORWARDEDHEADERS__ENABLED=true` in production.
- [ ] Restrict trusted proxy ranges with `SECURITY__FORWARDEDHEADERS__KNOWNNETWORKS__*`; do not enable unknown proxies on public networks.
- [ ] Capture IP whitelist supports exact IP and CIDR; use the narrowest `Security:CaptureIpWhitelist` values for the deployment network.
- [ ] Redis is shared by cache, fixed-window rate limiting and retry queue; when Redis is unavailable, API rate limiting falls back to a process-local fixed window, so multi-replica deployments should restore Redis promptly.

### 3.2 0.2.0 发布检查清单

- [ ] API、AI 使用 `v0.2.0` 或基于本版本构建的现场标签；通用提供方模拟器镜像仅在 `dev-tools` 测试环境启用。
- [ ] PostgreSQL 镜像使用 `pgvector/pgvector:pg16` 或内部批准的等价版本，目标库中 `vector` 和 `pg_trgm` 扩展可用。
- [ ] 升级前已完成 PostgreSQL 备份和恢复可用性确认；已有数据库仅执行 `migrate`，未执行仅适用于空库的 `bootstrap`。
- [ ] 迁移 `001` 至 `024` 全部 applied，`status --fail-on-pending --fail-on-drift` 返回 pending 0、unknown/drift 0。
- [ ] 默认向量配置为 `VECTOR_INDEX_READ_ENGINE=pgvector`、`VECTOR_INDEX_WRITE_MODE=pgvector`、`VECTOR_INDEX_ALLOW_LEGACY_READ_FALLBACK=false`。
- [ ] ArangoDB 图数据库使用独立的 `ARANGO_GRAPH_DB`、`ARANGO_GRAPH_USER` 和高强度 `ARANGO_GRAPH_PASSWORD`，且 API 图账号仅具有目标图数据库权限。
- [ ] 已在真实 ArangoDB 环境验证图初始化、Outbox 追平、全量重建和受限深度查询。
- [ ] 每个媒体解析提供方的出站 `secret_ref` 与入站 `webhook_secret_ref` 已分离，二者均引用环境变量、配置或 Secret，数据库中没有明文密钥。
- [ ] `MEDIA_ANALYSIS_PUBLIC_WEBHOOK_URL` 是提供方可访问的 Aura HTTPS 地址，Webhook HMAC、时间戳和 nonce 防重放已通过正反例测试。
- [ ] 提供方访问目标已加入 `MEDIA_ANALYSIS_OUTBOUND_ALLOWED_HOST_*`；只在确有需要时启用私网访问或明文 HTTP。
- [ ] 媒体 HTTP 超时、重试、熔断、并发上限、请求/响应体积和制品下载限制符合提供方 SLA 与现场带宽。
- [ ] 全局 readiness 显示 PostgreSQL/pgvector 可用，媒体解析 Worker 心跳正常，Inbox/Outbox 无异常积压或死信。
- [ ] 租户管理员只能读取和操作授权租户；事件重放、向量迁移、图管理和全局 readiness 仍由高权限账号控制。
- [ ] 生产经 Ingress/nginx/TLS 终止时保持 `Security__Cookies__ForceSecure=true` 和 `Security__ForwardedHeaders__Enabled=true`，可信代理范围已收窄。
- [ ] Redis 可用于缓存、分布式限流和重试队列；多副本部署不得长期依赖进程内限流降级。
- [ ] AI 图片限制 `AURA_AI_MAX_IMAGE_BASE64_CHARS`、`AURA_AI_MAX_IMAGE_PIXELS`、`AURA_AI_ALLOWED_IMAGE_FORMATS` 与最大相机载荷匹配。
- [ ] 发布前已通过后端构建/测试、AI pytest、前端 lint、Compose 配置解析，并按 `docs/2026-07-22-0.2.0发布说明与验收记录.md` 补齐真实 ArangoDB、目标浏览器和 Linux 脚本验收。

## 4. 健康与就绪

基础健康检查：

```powershell
powershell -ExecutionPolicy Bypass -File .\docker\check.ps1
```

脚本会检查：

- AI `/live`
- AI `/ready`
- API `/api/health`

业务就绪检查使用：

- `GET /api/ops/readiness`
- 需要超级管理员登录
- 用于检查 JWT、HMAC、AI、告警通知、数据库等关键配置；多 AI 节点会返回 `configuredNodes`、`reachableNodes`、`modelLoadedNodes` 与节点列表。
- 多 AI worker 地址优先在前端“运行配置”页面维护，保存后立即写入数据库并热生效；`.env.docker` 的 `AI_BASE_URLS` 仅作为启动兜底。

## 5. 数据库升级迁移

数据库升级迁移指 PostgreSQL 结构从旧版本升级到当前版本，不是服务器搬迁。当前版本使用 `backend/Aura.DbMigrator` 与 `schema_migrations` 表管理增量脚本。

上线标准流程：

1. 备份目标库，并确认备份可恢复。
2. 在维护窗口内先检查状态：

```powershell
dotnet run --project backend/Aura.DbMigrator -- status --fail-on-drift
```

3. 执行升级：

```powershell
dotnet run --project backend/Aura.DbMigrator -- migrate --command-timeout 300 --lock-timeout 60
```

4. 升级后验证没有待执行脚本：

```powershell
dotnet run --project backend/Aura.DbMigrator -- status --fail-on-pending --fail-on-drift
```

Docker 部署中，`db-migrate` 会在 API 启动前自动执行同一套 `migrate` 命令，并使用 PostgreSQL advisory lock 防止并发升级。本机开发使用 `python start_services.py` 时也会在启动 AI/API 前自动执行 `migrate`；直接 `dotnet run --project backend/Aura.Api` 不会自动迁移，必须先手动执行迁移器。可通过 `.env.docker` 或 `.env` 调整：

- `DB_MIGRATION_COMMAND_TIMEOUT_SECONDS`
- `DB_MIGRATION_LOCK_TIMEOUT_SECONDS`

注意事项：

- `bootstrap` 只用于空库初始化，禁止对已有生产库执行。
- 已上线执行过的 `database/migrations/*.sql` 不得改写；迁移器会校验 checksum，发现漂移会失败。
- 如果 `status --fail-on-drift` 失败，表示数据库记录了当前交付包不存在的迁移版本，应先停止发布并核对交付包。
- 如果迁移失败，单个脚本会回滚；修复后重新执行 `migrate`。

## 6. AI 生产检查

- [ ] `docker network ls` 可看到外部网络 `gpu-bridge`，GPU 服务共享模型目录内存在 `person_reid/osnet_x1_0_v1.onnx`，或已按现场实际值覆盖 Compose 同名环境变量。
- [ ] `GET /ready` 返回 `model_loaded=true`。
- [ ] ArangoDB 可连接，`ARANGO_DB` 存在。
- [ ] 如部署多个 AI worker，已由超级管理员在前端“运行配置 -> AI 推理节点”维护地址；`GET /api/ops/readiness` 中 `reachableNodes` 与 `modelLoadedNodes` 符合预期。
- [ ] 数据库迁移已包含 `007_add_sys_config.sql`，确保 `sys_config` 表存在；如该表不可用，系统只能回退启动配置。
- [ ] 多 AI worker 共用同一个 ArangoDB，并保持 `AURA_AI_REQUIRE_ARANGO=true`。
- [ ] 如使用 `/ai/extract-file`，API 落盘目录在所有 AI worker 容器内同路径可读，或已改用内联 Base64。
- [ ] 检索接口限流与队列参数符合现场并发。
- [ ] 生产环境默认关闭详细内部错误输出，必要时短时开启排障。
- [ ] 已执行 AI 巡检：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\ops\aura-ops.ps1 ai-check
```

### 6.1 AI image input limits
- [ ] AI image input limits are set for the expected camera payloads: `AURA_AI_MAX_IMAGE_BASE64_CHARS`, `AURA_AI_MAX_IMAGE_PIXELS`, `AURA_AI_ALLOWED_IMAGE_FORMATS`.
- [ ] `/ai/extract` invalid images return `HTTP 400/code=40002`; oversized images return `HTTP 413/code=41301`.
## 7. 回归与压测

统一入口：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\ops\aura-ops.ps1 readiness
powershell -ExecutionPolicy Bypass -File .\scripts\ops\aura-ops.ps1 capture-regression
powershell -ExecutionPolicy Bypass -File .\scripts\ops\aura-ops.ps1 full-check
```

其中：

- `readiness`：上线就绪检查
- `capture-regression`：抓拍链路回归
- `full-check`：全系统联调与压测

## 8. 数据与停机

`docker/down.*` 默认保留命名卷，数据不会丢失。只有确认需要清空 PostgreSQL、Redis、ArangoDB 与 API storage 数据时，才使用：

```powershell
powershell -ExecutionPolicy Bypass -File .\docker\down.ps1 -Volumes
```

该操作会删除命名卷，生产环境慎用。

## 9. 断网后的离线更新

在联网构建机执行：

```powershell
powershell -ExecutionPolicy Bypass -File .\docker\build-images.ps1
powershell -ExecutionPolicy Bypass -File .\docker\offline-pack.ps1
```

将 `docker/dist/aura-offline-<时间戳>/` 上传到已断网服务器后执行：

```powershell
docker load -i aura-images.tar
docker compose --env-file .env.docker -f docker-compose.yml up -d --no-build
```

默认保留命名卷，更新不会清空数据库和运行数据。
