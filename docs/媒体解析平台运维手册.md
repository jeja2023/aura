# Aura 媒体解析平台运维手册

本文是通用媒体解析控制面、可靠事件入口、pgvector 向量索引和 ArangoDB 关系图的生产运维入口。架构与开发约束见 [通用媒体解析与多模数据架构开发计划](通用媒体解析与多模数据架构开发计划.md)。

## 1. 数据职责

| 组件 | 权威职责 | 故障时行为 |
|---|---|---|
| PostgreSQL | 提供方配置、任务、订阅、Inbox/Outbox、业务事实、模型元数据 | 入口返回可重试错误，不确认外部事件 |
| pgvector | PostgreSQL 内的 512 维业务向量和检索索引 | 结构化事件仍可落库，向量检索明确返回失败 |
| ArangoDB | 从 PostgreSQL Outbox 派生的空间、访问、共现和转移关系图 | PostgreSQL 继续工作，Outbox 积压，恢复后自动追平或全量重建 |
| Redis | 缓存、限流和实时分发 | 正确性仍由 PostgreSQL 保证，实时能力降级 |

生产默认使用 `VECTOR_INDEX_READ_ENGINE=pgvector`、`VECTOR_INDEX_WRITE_MODE=pgvector`、`VECTOR_INDEX_ALLOW_LEGACY_READ_FALLBACK=false`。旧 Arango 向量桥只用于迁移或经审批的短时回滚，不属于目标稳态。

## 2. 上线配置

必须替换 `.env.docker` 中所有 `REPLACE_*` 值，并重点检查：

- `POSTGRES_*`、`ARANGO_GRAPH_*` 使用不同的最小权限账号。
- `MEDIA_ANALYSIS_PROVIDER_SECRET` 是 Aura 调用外部提供方的凭据；`MEDIA_ANALYSIS_WEBHOOK_SECRET` 是提供方回调 Aura 的 HMAC 凭据，二者不得复用。
- 数据库中只保存 `env://`、`config://` 或 `secret://` 引用，不保存明文密钥。
- HTTPS 提供方域名写入 `MEDIA_ANALYSIS_OUTBOUND_ALLOWED_HOST_0..2`。只有确需访问内网提供方时才开启私网访问，HTTP 仅限隔离开发环境。
- mTLS 证书通过只读卷挂载，密码通过 `MEDIA_ANALYSIS_MTLS_CERTIFICATE_PASSWORD_ENVIRONMENT_VARIABLE` 指向容器环境变量。
- `GRAPH_ENABLED=true` 时，图账号只对 `ARANGO_GRAPH_DB` 授予读写权限。

提供方凭据格式和轮换顺序见 [提供方凭据契约](contracts/media-analysis-provider-credentials.md)。

## 3. 部署与迁移

上线前：

```powershell
dotnet run --project backend/Aura.DbMigrator -- status --fail-on-drift
docker compose --env-file .env.docker -f docker/docker-compose.yml config --quiet
```

部署时 `db-migrate` 会持有 PostgreSQL advisory lock 并在 API 启动前应用迁移。部署后必须执行：

```powershell
dotnet run --project backend/Aura.DbMigrator -- status --fail-on-pending --fail-on-drift
```

`bootstrap` 仅用于空库。任何已运行的生产库只能使用 `migrate`。

## 4. 就绪与指标

超级管理员调用 `GET /api/ops/readiness` 或 `GET /api/media-analysis/ops/readiness`。结果分别包含 pgvector、提供方与订阅、Inbox、Outbox、后台 Worker 和 Arango 图状态。

启用 `OPS__METRICS__EXPOSEPROMETHEUS=true` 后重点采集：

- `aura_media_provider_operations_total`、`aura_media_provider_operation_duration_seconds`
- `aura_media_inbox_transport_delay_seconds`、`aura_media_inbox_processing_delay_seconds`
- `aura_media_backlog_messages`、`aura_media_backlog_oldest_age_seconds`
- `aura_media_job_outcomes_total`、`aura_media_job_duration_seconds`
- `aura_vector_search_total`、`aura_vector_search_duration_seconds`、`aura_vector_search_hits`
- `aura_graph_projection_total`、`aura_graph_query_total`、`aura_graph_query_duration_seconds`
- `aura_graph_rebuild_total`、`aura_graph_rebuild_documents`
- `aura_background_worker_healthy`、`aura_background_worker_last_success_timestamp_seconds`

建议告警：Inbox/Outbox 最老积压持续增长、dead-letter 大于零、流心跳超时、Worker 不健康、提供方超时率升高、向量失败率升高、图查询超时或图投影失败。

## 5. PostgreSQL 与 pgvector 备份恢复

使用与服务端主版本一致的 `pg_dump` 创建自定义格式备份：

```powershell
docker exec aura-pgsql pg_dump -U postgres -d aura -Fc -f /tmp/aura.dump
docker cp aura-pgsql:/tmp/aura.dump .\backup\aura.dump
```

恢复必须在隔离环境先演练。创建空目标库并恢复后，验证扩展、迁移和向量维度：

```sql
SELECT extversion FROM pg_extension WHERE extname='vector';
SELECT COUNT(*) FROM feature_embedding WHERE vector_dims(feature)<>512;
SELECT version,name,checksum FROM schema_migrations ORDER BY version;
```

恢复完成后运行迁移状态检查、API readiness、向量样本检索和业务事实抽查。不要只恢复 `feature_embedding`；模型、抓拍、事件和租户外键必须保持同一备份时间点。

## 6. ArangoDB 恢复与全量重建

ArangoDB 是派生图，优先从 PostgreSQL 全量重建。超级管理员调用：

```http
POST /api/graph/rebuild
Authorization: Bearer <token>
```

查询 `GET /api/graph/projection/status`，直到重建记录为 `completed`，再抽查点位路径、人员访问和共现查询。重建期间业务事实和 pgvector 不停写；图查询应按部署策略返回不可用或旧版本结果。

若需要保留 Arango 快照，使用同版本 `arangodump`/`arangorestore` 备份 `ARANGO_GRAPH_DB`。恢复后仍要核对投影检查点；检查点落后时让 Outbox 自动追平，无法证明一致时执行全量重建。

## 7. 事件与图投影重放

管理页“事件收件箱”和“关系图”支持按租户操作。API 可按事件 ID、时间范围或状态重放 Inbox；只能重放 `dead_letter`、`retry_wait`、`unsupported` 等非成功状态，幂等键保证不会重复业务副作用。

图 Outbox 使用 `POST /api/graph/outbox/replay` 按租户和状态恢复。重放前先排除 Arango 凭据、网络、集合定义或数据错误，否则只会再次进入退避和死信。

重放后核对：

```sql
SELECT status,COUNT(*),MIN(received_at) FROM media_analysis_inbox GROUP BY status;
SELECT status,COUNT(*),MIN(created_at) FROM integration_outbox WHERE event_type LIKE 'graph.%' GROUP BY status;
SELECT status,last_outbox_id,last_projected_at,last_error FROM graph_projection_checkpoint;
```

## 8. 故障演练

每次大版本上线前在隔离环境完成：

1. 重复投递同一事件 100 次，确认只有一个 Inbox 和一个业务副作用。
2. 在 Inbox 处理和图投影期间停止 API 实例，等待租约过期并确认其他实例接管。
3. 暂停 ArangoDB，确认 PostgreSQL 任务和事件仍落库、Outbox 积压；恢复后确认自动追平。
4. 暂停 PostgreSQL，确认 Webhook 返回可重试错误；恢复后由模拟提供方重投成功。
5. 模拟提供方返回 429、500 和超时，确认重试、熔断和任务错误可见。
6. 从备份恢复 PostgreSQL，执行图全量重建和 Inbox/Outbox 重放抽查。

演练记录必须包含镜像版本、硬件、数据量、开始/恢复时间、积压峰值、追平耗时和失败明细。

## 9. 容量扩展

- Inbox/Outbox 持续积压时先判断下游故障还是消费能力不足；扩 API 副本前确认所有 Worker 使用数据库租约和 `SKIP LOCKED`。
- pgvector 索引参数必须按实际向量数量、租户过滤选择性和 Recall@K 评测调整。扩容后重新运行影子评测，不以单次延迟代替质量指标。
- 图查询达到深度、行数或超时上限时应收紧业务查询，不取消保护上限。大规模关系分析使用离线任务。
- 媒体归档使用共享对象存储或共享卷；多实例不能依赖各自本地临时文件。
- 达到既定保留期后分批归档事件和媒体，保留 PostgreSQL 主键、模型版本、校验和及对象存储引用。

## 10. 回滚

应用回滚不得回退已提交的迁移文件。先恢复上一版本应用，并保持新表不删除。向量读写只有在 pgvector 故障且旧索引仍经验证时，才临时切换 `VECTOR_INDEX_READ_ENGINE=legacy-arangodb`、`VECTOR_INDEX_WRITE_MODE=dual` 和回退开关；恢复 pgvector 后立即回切并运行补偿队列与影子评测。

Arango 图版本异常时关闭 `GRAPH_ENABLED` 或暂停图查询，保留 Outbox，修复后全量重建。禁止把图数据反向覆盖 PostgreSQL 权威事实。
